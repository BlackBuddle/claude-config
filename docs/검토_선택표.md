# 검토 선택표

작성: 2026-11-14. 상황 1개에 명령 1개를 고른다. 표에 없는 상황은 사용자에게 묻는다.

## 0. 공통 규칙

- Claude는 작업 끝에 검토 명령 1개와 필요한 노력 수준(보통 high)을 같이 제안한다.
- 사용자가 노력 수준을 바꾸고 "변경함"이라고 답하면 실행한다. 이 답 1번이 승인이다. 다시 묻지 않는다.
- 검토는 테스트와 실제 장치 시험을 대신하지 않는다.
- 2개 이상의 줄이 맞으면 더 엄격한 명령 1개를 고른다: `/security-review` > `/code-review high` > `/ponytail-review`.

## 1. 코드 검토

| 상황 | 명령 |
|---|---|
| 변경 1건을 끝냈다 (평소) | `/ponytail-review` |
| 큰 변경을 끝냈다. 병합이나 배포 전이다 | `/code-review high` |
| 외부 입력, 네트워크, 인증, 파일 삭제를 다루는 코드다 | `/security-review` |
| 단계 1개를 끝냈다. 저장소 전체를 점검한다 | `/ponytail-audit` (크기 M·L은 2절의 `egm-drift-report`를 먼저 한다. 크기 S는 테스트만 한다) |
| 중복이 보인다. 코드가 길어졌다 | `/simplify` |
| 장치(Jetson, 로봇)를 움직이는 코드다 | `/code-review high` + 실제 장치 시험 |
| 설계 문서가 아닌 문서만 고쳤다. 1줄만 고쳤다 | 검토하지 않는다 (설계 문서는 2절을 따른다) |

## 2. 설계 검토 (EGM)

EGM(google/elephant-goldfish-model, 플러그인 `egm@egm`)으로 설계 문서를 검토한다. 2026-11-14에 벗(Beot) 재설계안으로 시험했고 작동을 확인했다.

- 설계 문서는 프로젝트의 `PLAN.md`다. EGM은 검토에만 쓴다. EGM의 `brainstorm`과 `draft`는 쓰지 않는다.

| 상황 | 명령 |
|---|---|
| 크기 S 프로젝트 | 검토하지 않는다 (사용자만 검토한다) |
| 크기 M·L의 새 설계 문서를 썼다 | 구현 전에 `/egm:egm-review <문서>` 1회 |
| 설계 문서를 크게 고쳤다 | `/egm:egm-review <문서>` 다시 1회 |
| 크기 M·L의 단계 1개를 끝냈다. 오래 쉰 프로젝트를 다시 시작한다 | `/egm:egm-drift-report <폴더>`. 그 뒤 1절의 `/ponytail-audit` |
| 설계 문서가 코드보다 낡았다 | 멈춘다. 사용자에게 재확인받는다. 문서 갱신을 요청한다 |

- 보고서 폴더: 검토마다 폴더를 따로 쓴다 (`egm_review/<날짜>_<문서 이름>/`). 같은 폴더에 쓰면 다른 검토의 보고서를 덮어쓴다.
- 문체 검토자(`egm-style`)는 기본 검토에서 뺀다. 사용자가 요청할 때만 부른다. 이유: 문체 지적이 많아 설계의 문제를 가린다. 문체는 사용자의 문체 규칙이 다룬다.

- EGM 스킬은 Claude의 직접 호출이 막혀 있다 (`disable-model-invocation`). 그래서 사용자가 승인하면 Claude가 이렇게 실행한다:
  1. `~/.claude/plugins/cache/egm/egm/<버전>/skills/<스킬 이름>/SKILL.md`를 읽는다.
  2. 그 파일의 절차를 그대로 따른다. 검토자는 `egm:*` 서브에이전트로 만든다.
  3. 사용자가 명령을 직접 입력할 필요는 없다. 직접 입력해도 된다 (`/egm:egm-review <문서>`).
- 우선순위: 사용자의 최신 결정(`docs/결정_기록.md`) > 설계 문서(`PLAN.md`) > 코드 · ROADMAP.md · HANDOFF.md. 결정이 설계 문서를 바꾸면 같은 세션에서 설계 문서를 고친다.
- 검토 지적과 사용자의 결정은 `docs/결정_기록.md`에 쓴다.
