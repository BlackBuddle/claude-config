# 통합 작업 방식 — 계획 문서 + 단계별 세션

> **위치**: `~/.claude/docs/통합_작업방식.md` (전역). 전역 `CLAUDE.md`의 "Work method" 절이 요약이고, 이 문서가 전체 내용이다. 프로젝트에 복사하지 않는다.
> 처음 적용하면 **2절**부터, 이미 적용된 프로젝트면 **4절**부터 따른다.

## 0. 한눈에

```
① 계획 (PLAN 확정) → ② 단계 나누기 (M0 = 가장 위험한 것)
→ ③ 단계마다 작업 세션 (읽기 → 계획 승인 → 작업 → 시험 → 기록 → 인계)
→ ④ 단계 끝 심사 (판정 → 결과·회고 → 다음 단계)
```
- **왜**: 대화가 길어지면 매 요청마다 앞 대화를 다시 보내 토큰이 커지고 앞 내용을 놓친다 → 세션을 짧게 끊고 **문서가 기억을 맡는다**.
- **세션 종류** (혼합형)
  - **작업 세션**: 구현·시험·인계. 단계 안에서는 HANDOFF.md로 다음 작업 세션에 이어 준다(연쇄).
  - **총괄 세션**: 계획·단계 심사·큰 방향 변경만. **필요할 때 열고 일이 끝나면 닫는다**(계속 살려 두지 않음). 보고는 대화가 아니라 **파일**(ROADMAP·결과 문서)로 받는다.

### 규모별 적용 (계획 때 하나를 고르고 CLAUDE.md에 적는다)
| | **S** (소) | **M** (중) | **L** (대) |
|---|---|---|---|
| 예 | 1주 이내 과제, 단계 2~3개 | 2~4주, 단계 4~6개 | 1달 이상, 단계 6개 이상 |
| 세션 구조 | 연쇄형만 (작업 세션이 단계 심사까지) | 혼합형 | 혼합형 + 필요하면 작업 세션 동시 진행 |
| 계획 검토 | 사용자만 | EGM 검토 1회 + 사용자 | EGM 검토 1회 + 사용자 |
| 숙의 (3절 7번) | 메인이 추천안·대안만 제시 | 에이전트 2명 | 에이전트 3명 이상 |
| 커밋 순서 (3절 6번) | 간단 | 기준점·고정 커밋 | 기준점·고정 커밋 |
| 단계 결과 기록 | ROADMAP에 3줄 | `docs/Mn_결과.md` | `docs/Mn_결과.md` |

## 1. 문서 구성 — 정본 1개 원칙

**같은 정보는 한 곳에만 적는다.** 다른 문서에는 내용 대신 위치만 적는다.

| 파일 | 정본으로 담는 것 | 언제 고치나 |
|---|---|---|
| `CLAUDE.md` | 프로젝트 안내, 규모(S/M/L), 문서 위치, 긴 문서의 절 목차 (**상태는 적지 않음**) | 구조가 바뀔 때 |
| `README.md` | 실행·시험·빌드 명령 | 명령이 바뀔 때 |
| `PLAN.md` | 기준 문서(설계 문서): 목표·원칙·범위·단계·완료 기준·위험과 대안·변경 이력 | 결정이 PLAN 내용을 바꿀 때 **그 세션에서 바로** (사용자 승인 후) |
| `ROADMAP.md` | **진행 상태**: 단계 표, 작업 현황, 사전 등록 기준, 시험 통과 수, 주차장 | 작업 하나 끝날 때마다 |
| `HANDOFF.md` | 다음 세션 인계 (최신 1개만, 8절 양식) | 세션 끝날 때마다 |
| `docs/결정_기록.md` | 사용자가 정한 것 (날짜순, 답 그대로) | 결정할 때마다 |
| `docs/Mn_결과.md` | 단계 결과 + 회고 (M/L) | 단계 끝 |

- **충돌 시 우선순위**: 사용자의 최신 결정(결정_기록) > PLAN(설계 문서) > 코드 · ROADMAP · HANDOFF. 어긋난 것을 발견하면 먼저 사용자에게 알리고 고친다.
  - 결정이 PLAN을 바꾸면 같은 세션에서 PLAN을 고친다. 그래서 PLAN은 항상 최신 결정을 담는다.
  - PLAN이 코드보다 낡았으면 멈춘다. 사용자에게 재확인받은 뒤 PLAN 갱신을 요청한다.

## 2. 계획 (총괄 세션 — S는 첫 세션)

1. 사용자와 목표를 정리하고 `PLAN.md` 초안을 쓴다. (M/L: 큰 꿈 A안 · 안전한 B안 두 개를 비교해도 좋다)
2. 검토(규모표대로. M·L의 EGM 검토는 `~/.claude/docs/검토_선택표.md` 2절을 따른다) → 사용자 결정 → 고침 → 상태 **'확정'**.
3. `ROADMAP.md`(부록 C 틀), `HANDOFF.md`, `CLAUDE.md`, `README.md`를 만든다 → 새 작업 세션.

**PLAN.md 필수 장**
| 장 | 내용 |
|---|---|
| 목표 · 원칙 | 한 줄 목표 + 판단이 갈릴 때 돌아올 원칙 3~7개 |
| 범위 (동결) | 이번에 만드는 것 목록 |
| 단계 표 | 단계별 내용과 **완료 기준**(확인 방법까지) |
| 위험과 대안 | 단계별로 막히면 쓸 대안 |
| 자르기 순서 | 넘칠 때 먼저 뺄 것 순서 + **절대 안 자르는 것** |
| 변경 이력 | 버전(vX.Y)마다 무엇이 왜 바뀌었는지 |

**단계 설계 규칙**
- **첫 단계(M0) = 가장 위험한 것**: 이게 안 되면 나머지가 소용없는 기술을 빈 화면·최소 코드로 먼저 확인.
- **완료 기준은 재어 볼 수 있게**: "잘 보임"(X) → "400px로 줄여도 1초 안에 찾음"(O), "잘 동작"(X) → "10번 중 10번 성공"(O).

## 3. 공통 규칙

1. **단계 순서대로**, 완료 기준을 통과해야 다음 단계로. 이월은 사용자 승인 예외로만.
2. **작업 전 계획 승인**: 만들 파일 · 설치할 것 · 검증 방법을 짧게 보여 주고 승인받는다. 계획과 필요한 노력 수준을 한 메시지에 쓴다. 사용자의 "변경함" 1번이 둘 다 승인한다.
3. **요청한 것만 고친다.** 다른 파일을 건드렸으면 먼저 보고.
4. **늘 그 자리에서 확인받는 일**: push · 원격 덮어쓰기 · 이슈/PR · 릴리스 빌드 · 삭제 등 되돌릴 수 없는 작업 · 범위·방향 변경. 커밋은 확인 후(또는 8절 미리 승인). 비밀번호·키·토큰은 파일·문서·커밋에 남기지 않는다.
5. **사전 등록**: 완료 판정 전에 ROADMAP의 해당 단계에 명령 · 조건 · 합격선 · 미달 처리를 적고 고정한다.
   - 결과를 본 뒤 기준을 바꾸지 않는다. 꼭 바꿔야 하면 사용자 승인 + "사후" 표시 + 원래 결과 보존.
   - 미달 후 코드를 고쳤으면 **같은 기준으로** 다시 판정한다.
6. **커밋 순서**
   - S: 구현 → 시험 → 커밋(확인 후)
   - M/L: 구현 → 시험 → 리뷰 기준점 커밋 → 리뷰·수정 → 코드 고정 커밋 → 공식 판정 → 결과 기록 → push(확인 후)
   - 리뷰 명령은 `~/.claude/docs/검토_선택표.md`의 표로 고른다.
7. **숙의**: 확정 결정 변경 · 판정 미달 · 되돌릴 수 없는 작업 · 큰 재작업이면 → (규모표 인원) 독립 분석 → **추천안 + 반대 의견 + 거절 시 대안**을 사용자에게.
8. **질문은 번호를 붙이고**, 질문마다 추천안 1개 + 이유. 답은 그대로 `결정_기록.md`에.

## 4. 작업 세션 시작

1. **읽기**: `HANDOFF.md` → `ROADMAP.md` 해당 단계 → `결정_기록.md` 최근 항목 → `PLAN.md` **필요한 절만**. 이전 대화 기록은 읽지 않는다.
2. **실제 상태 대조**: `git status` · `git log -5`가 HANDOFF의 "지금 위치"와 맞는지 확인. 다르면 먼저 알린다. (git이 없으면 부록 B)
3. **비정상 종료 감지**: 커밋 안 한 변경이 HANDOFF에 없거나, HANDOFF 날짜가 마지막 커밋보다 오래됐으면 → 6절 "비정상 종료 복구".
4. 이번 세션 계획과 필요한 노력 수준을 한 메시지에 짧게 보여 주고 승인받는다 ("변경함" 1번). HANDOFF의 "미리 승인된 것"은 다시 묻지 않는다(8절 조건 안에서).

## 5. 작업 세션 진행

- **작업 하나 끝날 때마다**: ROADMAP 진행 현황 갱신 + 보고 — 바뀐 파일(링크) · 실행 방법 · 확인한 것 / 못 한 것 · 남은 일.
- **자동 시험**: 사용자 화면을 방해하지 않게(창 없이, 백그라운드. 예: PyQt는 `QT_QPA_PLATFORM=offscreen`). 통과 수를 늘 기록(예: 62/62).
- GUI 프로젝트는 부록 A 실화면 O/X.
- 새 아이디어는 바로 넣지 않고 주차장으로(7절).
- 큰 파일 · 긴 로그는 필요한 부분만 읽는다.
- **세션 나누기 체크리스트** — 하나라도 해당하면 8절대로 인계하고 새 세션 (기본값, 프로젝트에 맞게 CLAUDE.md에서 조정):
  - [ ] ROADMAP 작업 3개를 끝냈다
  - [ ] 단계 안의 큰 구분점(기능 묶음 하나 완료)에 왔다
  - [ ] 앞에서 정한 것을 다시 묻거나 잊는 징후가 보인다
  - [ ] 작업 성격이 바뀐다 (예: 구현 → 단계 심사)

## 6. 실패와 복구

- **같은 문제로 3번 고쳐도 안 되면 멈춘다** → 원인 추정 · 선택지 · 추천안을 사용자에게 (M/L은 숙의).
- **되돌리기 (롤백)** — 실행 전 사용자 확인:
  - 커밋 안 한 변경을 치워 두기: `git stash` (나중에 `git stash pop`으로 복원 가능 — 버리지 않으므로 먼저 이것을 쓴다)
  - 이미 커밋한 것을 되돌리기: `git revert <커밋>` (기록을 지우지 않고 반대 커밋을 만든다)
  - 기준점: 마지막으로 시험을 통과한 커밋 (M/L은 리뷰 기준점 커밋)
- **단계 미달**: PLAN의 "위험과 대안" → 자르기 순서 → 이월(사용자 승인) 순으로 검토.
- **비정상 종료 복구** (인계 전에 세션이 끊긴 경우):
  1. `git status` · `git diff` · `git log`와 ROADMAP 진행 현황으로 실제로 끝난 것을 파악한다.
  2. 사용자에게 "확인된 것 / 불확실한 것"을 보고한다.
  3. HANDOFF.md를 다시 쓴 뒤 이어서 진행한다.
  - 예방: 작업 하나 끝날 때마다 ROADMAP을 갱신하므로, 끊겨도 마지막 작업까지는 남는다.

## 7. 범위 변경

- **범위는 동결**: 새 아이디어는 ROADMAP의 **주차장**에 적는다(지우지 않음).
- **하나 넣으면 하나 빼기**: 작업량이 느는 변경은 자르기 순서에서 같은 크기를 빼야만 넣는다.
- **심사는 단계 끝**에 한다(5번 → 9절). 단, 사용자가 직접 정하면 바로: `결정_기록.md` → `PLAN.md` 고침 + 변경 이력 (같은 세션에서).

## 8. 인계 (세션 끝내기)

1. **깨끗한 지점**에서 멈춘다: 시험 통과 상태, 커밋은 확인 후.
2. `ROADMAP.md`를 갱신한다.
3. `HANDOFF.md`를 아래 양식으로 **새로 쓴다**(이전 내용은 지움).
4. **다음 세션을 연다**: 데스크톱 앱이면 메인 세션이 새 세션 제안(카드)을 만들고 사용자가 눌러 시작. 그 밖에는 사용자가 새 대화를 열고 시작 문구를 붙여 넣는다. 같은 프로젝트 폴더에서.

**미리 승인 규칙**
- **다음 1개 세션에서만** 유효하다. 대상을 구체적으로 적는다 (예: "로컬 커밋 — 2단계 시험 통과 시").
- push · 삭제 · 원격 작업은 미리 승인할 수 없다. 늘 그 자리에서 확인.
- 시험 실패 · 계획 변경 등 상황이 바뀌면 무효 → 다시 묻는다.

**시작 문구**
```
<프로젝트 폴더>에서 이어서 진행해.
`~/.claude/docs/통합_작업방식.md`의 "4. 작업 세션 시작"을 따르고, 먼저 HANDOFF.md를 읽어.
이번 세션: <작업 세션 / 총괄 세션(n단계 심사)> — <목표 한 줄>
배경: <최근 바뀐 것 · 정한 것 2~3줄>
```

**HANDOFF.md 양식**
```markdown
# 인계 (YYYY-MM-DD, <n단계> <n번째 세션>)

## 지금 위치
- 단계: <n단계 이름> — <진행 중 / 판정 대기 / 완료>
- 마지막 커밋: <해시> <제목> (push: 함/안 함)
- 작업 트리: <깨끗함 / 커밋 안 한 변경과 이유>
- 자동 시험: <xx/xx 통과> (명령: <README 참고 또는 명령>)

## 다음 세션이 할 일 (순서대로)
1. ...

## 미리 승인된 것 (다음 1개 세션만 유효)
- ...

## 사용자 확인이 필요한 것
- ...

## 꼭 알아야 할 사실 · 주의
- (최근 결정, 함정, 진행 중인 것)

## 코드 위치
- <파일>: <무엇이 있나>

## 읽을 곳
- PLAN: <절>, ROADMAP: <절>, 결정 기록: <날짜>, 결과: <파일>
```

## 9. 단계 끝 (S: 작업 세션이 직접 / M·L: 총괄 세션)

1. 완료 기준을 **사전 등록대로** 확인한다(자동 시험 + GUI면 O/X) → 통과 / 미달(미달이면 6절).
2. 결과를 기록한다 — 한 일 · 시험(통과 수 + O/X 표) · 다음 단계로 넘긴 것 · **회고**(잘된 것 / 문제 / 다음에 바꿀 것).
3. 회고의 교훈을 다음 단계 계획에 넣는다. (M/L: 단계 끝 점검은 `검토_선택표.md`를 따른다: `egm-drift-report` 뒤에 `/ponytail-audit`)
4. 주차장을 심사하고, PLAN이 바뀌었으면 변경 이력에 한 줄 + 버전.
5. 결과 · 문서를 커밋(확인 후) → push 확인.
6. 다음 단계 계획 초안을 HANDOFF에 적고 → 사용자 승인 → 새 작업 세션.

## 10. 토큰 아끼기

- 세션은 단계(또는 큰 구분점) 하나만. 새 세션은 문서만 읽고 시작한다.
- 긴 문서는 절 목차를 CLAUDE.md에 적어 두고 필요한 절만 읽는다.
- 에이전트는 규모표만큼만 쓰고, 노력 수준을 일에 맞춘다(목록·요약 = 낮게, 설계 판단 = 높게). 같은 확인을 반복하지 않는다.
- 보고는 결론 먼저, 짧게. 같은 내용을 다시 정리하지 않는다.

## 11. 결정 대기열 (2026-11-15 사용자 지시)

**왜**: 하위 세션마다 사용자가 결정을 내리면 결정이 흩어진다. 결정은 총괄 세션 1곳에서 내린다.

**하위 세션 (총괄 세션이 연 세션)**
1. 사용자에게 결정을 직접 묻지 않는다.
2. 결정 1개를 파일 1개로 쓴다: `~/.claude/decisions/<프로젝트>-<MMDD>-<HHMM>.json`. 파일 이름이 결정 번호다.
3. 등급을 정한다.
   - **가 등급** (되돌리기 쉽다: 이름, 내부 구현 방식): 추천안으로 진행한다. 파일은 사후 보고다.
   - **나 등급** (되돌리기 어렵다: 범위, 설계, 의존성, 3절 4번의 일): 그 작업을 멈춘다. 막히지 않은 다른 작업을 계속한다.
4. 답은 총괄 세션이 메시지로 보낸다. 답을 받으면 그대로 적용한다.

**파일 양식** (UTF-8)
```json
{
  "project": "Beot",
  "session": "<이 세션의 이름 또는 id>",
  "grade": "나",
  "question": "<질문 1문장>",
  "options": ["<선택지 1>", "<선택지 2>"],
  "recommend": 1,
  "reason": "<추천 이유 1줄>",
  "blocked": "<멈춘 작업. 가 등급은 빈 문자열>"
}
```
- `recommend`는 추천 선택지의 번호다 (1부터). 가 등급에서는 이미 적용한 선택지의 번호다.

**총괄 세션**
- 우측 "결정 랙" 패널이 대기열을 보여준다 (mod `decision-rack`, 명령 `/decisions`). 사용자가 선택지를 누르면 입력창에 `결정 <번호>: <답>` 1줄이 쓰인다.
- `결정 <번호>: <답>`을 받으면 번호마다 순서대로 한다:
  1. 해당 프로젝트의 `docs/결정_기록.md`에 질문과 사용자의 답 원문을 쓴다.
  2. 파일의 `session`에 사용자의 답 원문을 메시지로 보낸다. 보낼 수 없으면 사용자에게 알린다.
  3. 대기열 파일을 지운다.
- 가 등급의 답이 "반대"이면 하위 세션에 되돌리기를 지시한다.
